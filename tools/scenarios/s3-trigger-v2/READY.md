## Діагноз і його межа

У старому `trigger.chip.wasm` Node WebAssembly API бачить власний export `memory` і не бачить експорту `__indirect_function_table`. Офіційна інструкція Wokwi для custom chip задає `--import-memory` та `--export-table`: https://docs.wokwi.com/guides/custom-chips-to-wasm . Стара збірка викликала clang без обох параметрів. У старому native mock структура timer була оголошена власноруч з іншим порядком полів, ніж у реальному заголовку, і тест не перевіряв WASM ABI. Це конкретний дефект сумісності збірки та пробіл перевірки; без повторного реального Wokwi-запуску не доведено, що це єдина причина 0 D3. GPIO, інші помилки симулятора або інших рівнів ще не виключено.

v2 зібрано окремо з `--import-memory --export-table --no-entry`, вихідний C не змінювався. Actual WASM test `node test-wasm.js` запускає `chipInit`, читає конфігурації з імпортованої WASM-пам'яті та викликає обидва реальні callback через експортовану таблицю. Підтверджено перевірку 100 мкс, HIGH 60 мс, LOW і 100 мс паузи, відхилення короткого сигналу та ігнорування повторних фронтів. Це host mock інтерфейсу, не доказ роботи Wokwi.

Схема: PA7 → MARK (INPUT), PA7 → логічний D1; PIR (OUTPUT_LOW) → PB0, PB0 → D3; PA1 → D7. Фізичний вихід `pir` до PB0 не підключений. 100 мкс визначається часом моделі. Під час flash PA7 також HIGH: імпульси зараховуються лише всередині повного D1 з відповідним UART `EXPORT rows=64`. D7 — маркер обробки, а не гарантований LED; missing D7 звітувати як missing, не 0 мс.

## Межі єдиного запуску після нового дозволу

1. Відкрити тільки це власне робоче вікно, зберегти вибраною вкладку Wokwi, не змінювати конфіг або прошивку. Використовувати звичайну чинну ліцензію.
2. Одним процесом записати до нового окремого каталогу: `PYTHONPATH=Lab03/Work/python-packages python3 Lab03/Work/s3-trigger-fixture-v2/record.py --output Lab03/Work/s3-trigger-fixture-v2/S3-trigger-v2-01`. Стартувати з каталогу SP. Gate у тому самому екземплярі: 10 с MCU, правильний BUILD та ненульові ADC/IMU. У разі виявленого зворотного STATUS, відсутності прогресу 120 с host або 1800 с host — incomplete.
3. Після STATUS t >= 70000 мс команда `mode auto`, потім `history`; наступну history надсилати після повного повідомлення EXPORT. План: не менше 160 с MCU від першого STATUS і 45 повних EXPORT. Жорсткий максимум 300 с MCU: якщо ціль не досягнено, incomplete, включно з неповним in-flight history. 45 EXPORT не гарантують 30 вхідних фронтів. Не повторювати S1/S2 і не об'єднувати події між запусками.
4. Після завершення collector до Stop зберегти незмінні `uart.raw`, `commands.jsonl`, `manifest.json` і SHA256. Після спостережуваного Stop одразу скопіювати VCD до цього каталогу, хешувати, зафіксувати початок/кінець, видимість і часові обмеження. Не називати зупинку wall-clock скиданням MCU без даних.
5. `tools/validate_s3_events.py <uart.raw> <capture.vcd> --output <export-events.json>` та `tools/analyze_capture_lab3.py <capture.vcd> --output <capture-analysis.json>`: перевірити тривалість/повноту VCD, 64 рядки UART, D1 pairing, distinct D3 у кожному підтвердженому export, співставити D7 та вказати неоднозначні чи відсутні реакції. Успіх вимоги кількості — тільки >=30 реально зафіксованих придатних подій одного запуску; відсутність фронтів чи D7 є результатом перевірки, не latency=0.
6. Закрити лише своє зупинене вікно, перевірити свої порти, записати released/guiStopped з доказом. Результати S1/S2 не перезапускати. Flash ERROR не вважати успішним збереженням; фізичне відключення живлення не перевірене.
