# Межі super loop DeskLight

Стан 28.10.2026: нижче наведені підтверджені кодом/ARM-компонуванням властивості. Часові симптоми S3 ще потребують реального вимірювання на моделі. Гіпотези ОС не видаються за виконану ЛР4. Для кожної FR остаточний числовий вердикт ставиться лише після максимуму S3.

## L1. UART export утримує foreground

Симптом: PIR/ADC/IMU/control не запускаються, поки history надсилає рядки, FR-02/04/07/09 під ризиком. Доказ: Board export_history має цикл до 64 HAL_UART_Transmit, а board_step викликає command до сенсорів; tests не оголошують цю властивість MCU-виміром. Теоретична нижня межа для N байтів 8N1 дорівнює N×10/115200 с. Точні N та тривалість беруться з EXPORT реального run.

Причина: foreground не витісняє власну довгу функцію. Без ОС: передавати рядок частинами через TXE IRQ/DMA, з індексом та станом експорту; це додає стан, протокол ownership і відновлення. ОС: низькопріоритетна задача експорту й вища задача PIR з чергою даних. Ціна: стек задачі, ядро, перемикання та ризик переповнення черги. Гіпотеза ЛР4: PIR max <25 мс під час export за незмінного polling 20 мс, якщо UART driver не блокує IRQ. Перевірити тим самим D3→D7.

## L2. RX буфер має скінченний час захисту

Симптом: при довгому export команда губиться або відхиляється після overflow. Доказ: RX[128] із одним порожнім слотом має 127 bytes; при 115200 8N1 і без draining це 11.024 мс корисного буфера. USART IRQ продовжує прийом, але не виконує parser. Число фактичних втрат має дати rx_drop/ore у stress run.

Причина: єдиний споживач затриманий іншою foreground роботою; більший буфер лише переносить межу. Без ОС: збільшити буфер/IRQ parser/DMA і flow control; RAM, складніший ISR та resynchronization. ОС: пріоритетна command task може споживати незалежно від export. Ціна: окремий стек, queue/stream buffer і узгодження команд із Desk state. Гіпотеза: нуль rx_drop при заданому 10 command/s у S3; без flow control гарантії для необмеженого потоку немає.

## L3. Пам'ять обмежує перенесення в ОС

Симптом: flash-код має малий запас після резервування журналу. Доказ: ARM build-pilot-fix.log, 28 424/28 672 bytes коду й констант, лише 248 bytes; ще 4096 bytes виділено під journal. RAM linker used 9976/12288 включає 4096 stack і 512 heap reserve. Статичні реальні data/bss необхідно брати з size -A, а не додавати stack до size двічі.

Причина: додаткові черги та стеки ОС не безкоштовні; сама тіснота flash є апаратним обмеженням, а не доказом переваги ОС. Без ОС: скоротити текстові логи/formatting або розмір історії; втрата діагностики. ОС: окремі стеки спростять ізоляцію, але збільшать пам'ять. Ціна: ядро і сума stack reserves. Гіпотеза ЛР4: із тим самим MCU і журналом просте додавання ОС не вміститься без оптимізації; перевірити link map, не міняти MCU автоматично.

## L4. Внутрішня flash має один bank

Симптом: виконання flash-коду/ISR може зупинитися під час erase/program. Доказ: адреси journal 0x08007000..0x08007fff і один bank C031 у RM0490, Board flash_program/erase справді викликає HAL; жодного HAL_Delay для імітації немає. Фактична підтримка й час у Wokwi поки не підтверджені. Host integrity tests підтверджують тільки recovery алгоритму.

Причина: stalled instruction fetch не усувається foreground scheduler. Без ОС: виконувати критичний шлях і vectors із RAM, планувати save поза важливим інтервалом або зовнішня пам'ять. Кожне рішення має додатковий код/ресурс і потребує перевірки linker. ОС не усуває stall одного bank. Ціна ОС тут може бути без виграшу latency. Гіпотеза: перехід на RTOS без RAM-resident ISR не поліпшить максимальну flash-induced latency; порівняти D1→D7.

## L5. Час CPU відрізняється від часу корисних задач

Симптом: низька task share не означає idle CPU. Доказ: main безумовно викликає board_step у while(1), WFI відсутній, STAT loop рахує кожний прохід. task_permille=unavailable; awake_pct=100 є наслідком коду. Окрема GPIO-збірка показала 61,334% маркованих ділянок лише у своєму номінальному вікні; ISR усередині них і витрати маркерів включено. Енергоспоживання не вимірювалося.

Причина: polling виконується постійно. Без ОС: WFI разом із коректними TX interrupts і wakeup timer; потрібне уникнення race між перевіркою роботи й sleep. ОС: idle task/tickless може спати між готовими задачами. Ціна: tick/context overhead і перевірка wake sources. Гіпотеза: зменшити active CPU до <20% у S1, але порівнювати фактичний GPIO busy timer, не лише task_share; runtime енергетичний виграш не обіцяється.

## L6. Зміна розкладу зачіпає інтеграційний модуль

Симптом: додавання checkpoint і export потребувало змін Board command dispatch, accounting, scheduling, measurement names і Makefile. Доказ: git diff від 2b6659f та docs/tasks.md; переносимі worklog і Desk при цьому не включають HAL, що підтверджує check_project.py.

Причина: керування всіма періодами й спільним Desk state зосереджене в одному foreground. Без ОС: table-driven dispatch, callbacks та окремі FSM, ціна додаткових непрямих викликів і структур. ОС: задачі й черги дозволять локальні blocking flows, але Desk state доведеться явно передавати повідомленнями або захищати. Ціна: mutex ownership, deadlock/priority inversion та stack budget. Гіпотеза: новий періодичний споживач потребуватиме <=2 інтеграційних змін замість ручного включення в Board; оцінювати diff і складність, а не кількість рядків як якість.

Super loop тут дає одну точку зміни прикладного стану, один стек і простий порядок викликів. Звичайний рух має лишатися активністю в обох архітектурах. Потреба в ОС обґрунтовується виміряними порушеннями S3, не самим фактом наявності RTOS у курсі.
